# AGENTS.md - Developer & Agent Guidelines

This document outlines the architectural principles, behavioral guidelines, and best practices for AI Coding Agents and software engineers maintaining, extending, and debugging the **Micro-Orchestrator** project.

---

## 🏛️ Core Architecture Invariants

When making any modifications to this project, **the following invariants must be strictly preserved**:

### 1. Strict "Zero-Daemon Dispatcher"
- `dispatch.py` must remain **stateless** and complete execution within **< 0.1 seconds**.
- **Never** introduce `while True`, `time.sleep()`, or persistent daemon processes listening for schedules into `dispatch.py`.
- Dispatch triggering must rely entirely on operating-system-level schedulers (e.g., Linux `cron` or macOS `launchd`).

### 2. Zero Intrusion on Tasks
- `tasks/*/main.py` contains pure, standalone business logic. **Never** force tasks to import orchestrator SDKs or use decorators.
- Task status tracking (writing `RUNNING`, capturing `$?`, writing `SUCCESS` / `FAILED`, and redirecting logs) **must be executed entirely within the Bash execution chain via the `sqlite3` CLI**.

### 3. Strict Environment Isolation
- Each task directory should be treated as an isolated micro-project with its own `.venv` and `logs/`.
- Tasks must be invoked using their dedicated Python binary path, strictly avoiding cross-task dependency conflicts.

### 4. Database WAL Mode & Concurrency Guarantees
- `orchestrator.db` must always maintain `PRAGMA journal_mode=WAL;`.
- When adding or modifying tables, all `INSERT` operations must remain compatible with SQLite 3.35+ `RETURNING` syntax to allow the Bash chain to write state and retrieve primary key IDs in a single step.

### 5. On-Demand WebUI
- The Web server is designed to run on-demand (double-click `run_ui.command` to open, press `Ctrl+C` to exit when done).
- Never require a persistently running server to execute scheduled tasks; the `POST /api/run/{job_name}` API endpoint must reuse the identical standalone Bash chain generated by `dispatch.launch_job`.

## 🛠️ Development & Maintenance Guidelines

### 1. Standard Procedure for Adding a Task
1. Create a new directory under `tasks/`, e.g., `tasks/my_task/`.
2. Set up its isolated virtual environment:
   ```bash
   python3 -m venv tasks/my_task/.venv
   tasks/my_task/.venv/bin/pip install -r tasks/my_task/requirements.txt # if applicable
   ```
3. Write the business logic script: `tasks/my_task/main.py`.
4. Register the task in `jobs.yaml`:
   ```yaml
   - name: my_task
     schedule: "15 * * * *"
     dir: tasks/my_task
     python_bin: .venv/bin/python
     script: main.py
   ```
5. Verify execution:
   ```bash
   .venv/bin/python dispatch.py --run my_task
   ```

### 2. jobs.yaml Validation Rules
When modifying the `/api/config` validation logic in `server.py`, ensure the following checks are enforced:
- YAML syntax is valid.
- The root object contains a `jobs` list.
- `name` is required and globally unique.
- `schedule` passes validation via `croniter.is_valid()`.
- `dir` and `script` fields are present.
- File writing must use a tempfile + atomic rename pattern to prevent corruption from interrupted writes.

### 3. Log & Path Traversal Security
- When implementing log-reading endpoints (such as `GET /api/logs`), always protect against directory traversal attacks:
  ```python
  normalized = os.path.normpath(file)
  if normalized.startswith("..") or os.path.isabs(normalized):
      raise HTTPException(status_code=400, detail="Invalid path")
  ```

## 🧪 Common Testing & Verification Commands

```bash
# 1. Check database status and WAL mode
sqlite3 orchestrator.db "PRAGMA journal_mode;"
sqlite3 orchestrator.db "SELECT * FROM job_runs ORDER BY id DESC LIMIT 5;"

# 2. List all currently configured jobs
.venv/bin/python dispatch.py --list

# 3. Test successful task execution (should produce exit_code 0 and SUCCESS)
.venv/bin/python dispatch.py --run crm_sync

# 4. Test failing task execution (should produce exit_code 1 and FAILED, log containing traceback)
.venv/bin/python dispatch.py --run test_fail_job

# 5. Start the management API / Web server
./run_ui.sh
```
